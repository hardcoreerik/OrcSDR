# OrcSDR ESP-NOW integration plan — analysis only

`origin/main` at `897c60a3` runs the Tab5 ESP32-P4 application with ESP-Hosted 3.0.6 and `esp_wifi_remote` on its ESP32-C6. `ui/wifi_service.cpp` initializes the hosted transport and station Wi-Fi; the build embeds a pinned C6 image. The existing web control path accepts integer-Hz tune commands through `web_command.hpp`, but it is a single pending LAN command slot, not an ESP-NOW transport or a full radio state subscription. No ESP-NOW receiver exists in the OrcSDR Tab5 code reviewed here.

ESP-NOW should terminate on the **C6**, because the P4 has no native Wi-Fi radio. Espressif's ESP-Hosted 3.0.6 peer-data example shows a CustomRpc/peer-data channel, but that is only a candidate transport for carrying OrcControl frames or events between C6 and P4. It does not prove that the pinned C6 image implements ESP-NOW forwarding. An ESPHome hosted firmware overlay separately implements ESP-NOW through CustomRpc, showing feasibility but requiring source/license review and an independent design before adaptation. First prove C6 local ESP-NOW receive/transmit alongside the current hosted Wi-Fi firmware and determine whether peer-data can carry asynchronous receive events without disrupting the existing SDIO, Wi-Fi, or OTA flows.

Minimum production path, after that gate:

1. Add a small C6 ESP-NOW endpoint to the exact pinned hosted C6 source, gated by explicit pairing. Keep the existing Wi-Fi and hosted functions intact. Forward decoded frames or bounded raw frames over an established peer-data channel; reject malformed frames and unknown senders before routing them.
2. Add a P4 adapter that queues validated commands onto the existing radio/UI owning task. It should call the same tune/mode/gain/volume/squelch control operations used by local UI, respecting active radio route and frequency bounds. Do not alter RTL-SDR USB or DSP code.
3. Publish an authoritative state snapshot only after a command is applied, including dashboard ID, mode, frequency, step, gain, volume, squelch, and real signal if available. Publish again when the dashboard changes on the Tab5. Clear the valid-signal bit when unavailable. Return `RADIO_STATE` with the command sequence as ACK. Route `SET_DASHBOARD` through the existing dashboard opening path; reject unavailable destinations. Persist the last accepted sequence per peer to reject retries after lost ACKs.
4. Include C6 image revision/hash in the P4 build gate. Test upgrade/recovery and hosted link restart behavior before any release package.

Channel plan: ESP-NOW peer channel 0 uses the radio's **current** channel, not an automatic cross-channel broadcast. With infrastructure Wi-Fi, the C6's channel follows the access point; the Dial must discover or rescan to that channel. In offline mode the C6 must use a selected 2.4 GHz channel and advertise it during pairing; the Dial scans channels 1–11. Neither side should force a fixed channel while connected to an AP. Reconnect on AP channel change should rediscover and confirm state before controls resume. The prototype receiver stub is fixed to channel 1 for bench testing only.

Pairing UX: During first-run Tab5 boot/splash, offer an OrcDial pairing action when no peer is saved. Also expose **Connect OrcDial** in the Tab5 settings/connection UI, so pairing can be opened later without reboot. On the Dial, hold its button for at least four seconds to open pairing; provide an explicit **Connect** item on its touch connection screen as a second path. Both paths open bounded windows and require confirmation on both screens before saving the peer identity and shared key. Normal boots should reconnect saved peers automatically without opening pairing to strangers. For security, the current prototype saves MAC identity but has **no authentication or encryption**; it must not be treated as sufficient for production. Verify encrypted unicast peers, key provisioning, and reset/re-pair behavior on the real C6. Heartbeats and command ACK timeouts should mark the Dial offline; reconnection must request full state before the UI shows a live connection.

Acceptance gates: build the exact C6/P4 pair; receive and send ESP-NOW while associated to a changing AP and without an AP; prove channel rejoin, duplicate rejection, pairing consent, actual tuning and returned state, no fabricated RSSI, and no RTL-SDR/audio regressions on a physical Tab5. A successful Dial build or ESP32 stub test alone does not close any Tab5 gate.
